\section{Key learnings}

{\centering
\begin{tikzpicture}[font=\sffamily\footnotesize, >=stealth,
  box/.style={draw=branddeepteal, fill=brandteal!8, rounded corners=2pt, align=center, inner sep=3pt, text=brandnavy},
  arr/.style={->, thick, draw=brandnavy}]
\node[box, fill=brandcyan!12, text width=3.3cm] (w) {\textbf{Normal wallet} (CIP-30)\\signs, pays the fee,\\provides the collateral};
\node[box, fill=brandnavy!6, text width=3.0cm, right=6mm of w] (tx) {\textbf{One transaction}\\one redeemer:\\the declared action};
\node[box, text width=6.2cm, anchor=north west] (st) at ([xshift=7mm]tx.north east) {\textbf{State contract} (rules): action $=$ true change};
\node[box, text width=6.2cm, anchor=south west] (wa) at ([xshift=7mm]tx.south east) {\textbf{Wallet contract} (funds): payout $\le$ action};
\draw[arr] (w) -- (tx);
\draw[arr] (tx.east) -- (st.west);
\draw[arr] (tx.east) -- (wa.west);
\end{tikzpicture}\par
{\footnotesize\color{brandnavy!80} One action in Epora: two contracts read the same redeemer, and a normal wallet signs and pays.\par}}

\begin{itemize}[leftmargin=1.2em]
\item \textbf{Two contracts must agree on one action.} Both contracts read one redeemer, the declared action.
  The state contract proves that the action equals the true change to the wallet state.
  The wallet contract limits the payout to that action and has no permission logic, so a reviewer can check it by itself.
\item \textbf{One configurable contract replaces many bespoke ones.} Six features give 364 combinations of ``and'' and ``or'', and seven give 1,093.
  One contract for each combination is too much to build, test, and audit.
  So the whole configuration is one datum on one contract, and a new combination is data, not code.
\item \textbf{An open deposit address has edge cases.} Anyone can pay into the wallet with no datum, as into a normal address.
  But a sender can attach a datum hash, or pick a foreign stake credential that then collects the staking rewards of those funds.
  The contracts now pin the stake credential and reject datum hashes on outputs that stay in the wallet.
  An earlier whitepaper missed the datum-hash case and now records the correction.
\item \textbf{Script size needs its own design work.} A transaction may use at most 16,384 bytes, and the state script alone has 14,469 bytes.
  So the script is stored once as a reference script, in a 93-byte always-fail store at a fixed address.
  Each state transaction points to it.
  Without the reference, even the mint of a new wallet would exceed the limit.
  With both scripts as references, a payout to 15 beneficiaries used 9,925 signed bytes. With the wallet script inline, 2 beneficiaries used 11,163.
  With full traces the state script has 40,258 bytes, so the production build drops them.
  A size pass used standard-library helpers, callbacks, and shared checks (\pr{296}).
  It cut the state script from 15,936 to 14,428 bytes and the wallet script from 9,810 to 9,378 bytes.
\item \textbf{Caps and gates keep each action inside the limits.} The contracts cap the lists: 15 user and beneficiary records (at most 10 users), 15 streaming payments, and 5 assets in one allowance.
  The beneficiary checks compare every pair, so their cost grows with the square of the list.
  CI fails when a recorded cost moves by more than 1\%.
  The app checks each signed transaction against the size limit before it submits.
\item \textbf{A smart wallet still needs a normal wallet.} Today each action uses two wallets.
  A normal CIP-30 wallet signs, pays the fee, provides the collateral, and gets the change.
  CIP-30 does not cover script wallets, so the app shows the smart wallet's funds and previews each transaction.
  The CIP in Section~\ref{sec:next} aims to remove the second wallet.
\end{itemize}

\section{Next steps for the product}\label{sec:next}

\begin{itemize}[leftmargin=1.2em]
\item \textbf{Mainnet beta.} Run the beta with small funds, and close the open items from Section~2.
  On Mainnet, a notice says that the code has no external audit, and users cannot close it.
\item \textbf{A smart-wallet CIP.} EVM chains have smart-account standards, for example ERC-4337 and ERC-7579.
  We plan to draft a similar CIP for Cardano. It would define how a wallet finds a smart wallet, shows its funds and rules, and builds its actions.
  It can build on CIP-141 (Plutus wallets) and CIP-106 (multisig wallets), which both have the status Proposed.
  After an external audit, the Epora contracts could be the reference implementation.
\item \textbf{Audit funding.} We plan to fund the external audit after the community gives feedback on the CIP, if the audit is needed.
  This depends on the community and on the CIP implementations.
\item \textbf{Wallet integrations.} Follow up with the wallet teams that we contacted.
  At \mbox{TOKEN2049}, we plan to meet builders in person and collect their feedback.
\end{itemize}

\section{Final thoughts}

The proposal addressed the risk of losing all funds when a key or a backup is lost.
The delivered contracts, app, and API give Cardano users recovery and shared permissions without a custodian of funds.
We want this work to become the base of a smart-wallet standard for Cardano.
